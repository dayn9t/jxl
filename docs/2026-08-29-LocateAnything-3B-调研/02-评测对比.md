# NVIDIA LocateAnything-3B 调研报告（分工：评测与竞品对比）

调研日期：2026-08-29。调研人分工：benchmark 数字、竞品对比、效率指标、第三方独立评测。

信息源概览：核心 benchmark 数字已通过 **四方交叉验证**——arXiv 论文全文 HTML（arXiv:2605.27365v2）、NVIDIA 官方项目页、官方 GitHub `NVlabs/Eagle` 的 `Embodied/document/RESULTS.md`、以及独立中文技术博客（莫叶何竹）。所有数字原样引用。**注意：全部 benchmark 数字均为 NVIDIA 自评**，独立第三方定量复现目前几乎没有（详见第 6 节）。

## 1. 模型与发布时间线（背景速览）

- 架构：MoonViT（MoonViT-SO-400M，源自 Moondream，MIT 许可）视觉编码器 + Qwen2.5-3B-Instruct 语言解码器 + MLP projector；核心创新 Parallel Box Decoding（PBD），L=6 的 box-aligned 原子块并行解码（来源：HF 模型卡 https://huggingface.co/nvidia/LocateAnything-3B ；论文 https://arxiv.org/abs/2605.27365 ）。
- 参数量：官方命名 **3B**；HF 模型卡 Safetensors 侧栏写 **"Model size 4B params"**（BF16）——两处原样记录，疑似 3B LLM + 0.4B ViT 的合计口径差异（来源：HF 模型卡）。
- 发布时间线：arXiv v1 **2026-05-26**、v2 **2026-05-27**；GitHub/HF/Demo/技术报告均标注 **05/26/2026**；2026/06 宣布被 **ECCV 2026** 接收，并陆续发布 visual prompt LoRA 微调脚本与面向 A100/RTX 4090 的 `la_flash` 批量推理 runtime（来源：arXiv abs 页；HF 模型卡；https://github.com/NVlabs/Eagle/blob/main/Embodied/README.md ）。
- 训练数据：**12M 唯一图像 / 138M 查询 / 785M 框**；任务占比（按查询）：通用检测 66.9%（占框数 83.1%）、GUI 16.5%、指代 7.3%、OCR 3.6%、版面 3.5%、点定位 2.2%（来源：官方页、论文、RESULTS.md、HF 模型卡四方一致）。
- 许可：模型 **NVIDIA License（仅限非商业的学术/非营利研究）**；代码 Apache 2.0；Qwen2.5-3B-Instruct 组件受 Qwen Research License 约束（来源：HF 模型卡、Embodied README）。

## 2. 评测协议——先说清楚「可比性」这个大前提

这是本次调研最重要的发现之一，直接影响所有数字的解读：

1. **LocateAnything 论文不用 AP/mAP，全部用自定 F1 协议**：F1@IoU=0.5、F1@IoU=0.95、F1@Mean（多个 IoU 阈值平均）；pointing 任务用 F1@Point（点落入 GT 框/mask 即正确）（来源：https://arxiv.org/html/2605.27365v2 ；RESULTS.md）。
2. **因此其数字与公开榜单（mAP 口径或 ScreenSpot-Pro 官方 accuracy 口径）不可直接横向比较**。例如论文 Table 12 中 ScreenSpot-Pro 行的指标标注为 "Acc"（59.7/60.3/60.5），与 Table 3 的 F1 口径并存，论文内存在两种标注，读者需谨慎。
3. 论文中 Grounding DINO、DocLayout-YOLO、PaddleOCRv5 等专用模型的分数是**作者在 F1 协议下的重测**，非原论文 AP 成绩。
4. 速度指标 **BPS（Boxes Per Second）**：单张 NVIDIA H100、batch size 1、COCO、短边 840px、BF16 下测得（来源：论文 + 官方页）。论文**未报告首 token 延迟**，只有解码吞吐。

### 4.3 定位总结（事实+分析）

- **对 3B 级定位特化模型（Rex-Omni）**：速度 2.5×（12.7 vs 5.0 BPS），LVIS/密集/文档/GUI/pointing 全面占优；COCO@0.5、Dense200@0.5、HumanRef Mean 三处 Rex-Omni 或 SEED 更高。
- **对通用 VLM（Qwen3-VL/SEED1.5-VL 等）**：速度约 10×；密集检测、文档、GUI、pointing 大幅领先；但 SEED1.5-VL 在 LVIS/COCO@0.5、HumanRef Mean 仍更强——通用 VLM 的召回宽度优势仍在。
- **对经典/专用检测器**：COCO Mean F1 低于 Grounding DINO-Swin-T（54.7 vs 56.6），DocLayNet 低于 DocLayout-YOLO（76.8 vs 81.1）——**「YOLO/Grounding DINO 替代者」的说法只在开放词汇+语义组合查询+GUI/文档场景成立，纯封闭类别高吞吐检测并非其优势区**（此结论与 Medium 对比文观点一致，但该文 403 未直接核实，标注为未证实）。
- **对 GUI 专用大模型**：以 3B 打 32B（GUI-Owl-32B 58.0 vs 60.3）是其最有说服力的卖点之一。

### 5.1 吞吐（官方，单张 H100，batch=1，Hybrid）

| Qwen3-VL-4B | 1.1 |
| OVIS2.5-2B | 1.3 |
| Rex-Omni-3B | 5.0 |
| SDLM-B6（MTP 基线） | 5.5 |
| **LocateAnything-3B Hybrid** | **12.7** |
| LocateAnything-3B Fast（消融/Table 12） | 16.9 / 15.3 |
| LocateAnything-3B Slow | 4.3 |

密集场景扩展性：目标从 20 → 300 框，PBD 生成时间近乎平坦，吞吐从约 12 BPS 升至约 25 BPS，整体较 NTP 加速 **2×–6×**（论文 Fig.7）。**论文未报告首 token 延迟与端到端整图延迟**（记入 gaps）。

### 5.2 显存与硬件支持（HF 模型卡，2026-05-26）

- A100 4K 探针（3840×2160 街景、query=vehicle、batch_size=4、in_token_limit=25600、hybrid MTP）：`sdpa` 后端 8.2600 s / 峰值保留显存 **35.12 GB**；`la_flash` 后端 8.0314 s / **11.71 GB**。
- 支持硬件：Ampere（A100）、Hopper（H100）、Lovelace（L40、RTX 4090）、Blackwell；Linux only；BF16 + KV cache；TensorRT/TensorRT-LLM/Triton **尚不支持**；MagiAttention v1.0.5 仅 Hopper/Blackwell 加速 MTP。
- 输入上限：图像至 2.5K 分辨率、prompt 24K token、生成至 8192 新 token。

### 5.3 第三方实测部署（独立于 NVIDIA）

- **边缘 NPU（爱芯元智 AX8850，知乎「圈圈虫」，2026-07-16）**：整板功耗 <5W（8 核 Cortex-A55 + 24 TOPS@INT8 NPU，M5Stack AI PYRAMID PRO 开发板），经 Pulsar2 量化为 .axmodel 全离线运行；**图像编码约 1 s，LLM 生成约 9.5 token/s**；作者明确声明「**这不是实时检测方案**」，适用拍照分析/离线标注/产线抽检。量化模型发布于 `AXERA-TECH/LocateAnything-3B`（ModelScope/HF）。注意：该文由芯片生态方撰稿，属移植演示而非中性评测。来源：https://zhuanlan.zhihu.com/p/2061244136972457125 。
- **RTX 4090（openEuler/CSDN 部署记录）**：Kylin Linux Advanced Server V10 + RTX 4090（文中称 23GB 显存）、Driver 580.105.08、CUDA 13.0 部署成功。来源：https://openeuler.csdn.net/6a36bbcd662f9a54cb822e8b.html 。

## 6. 独立第三方评测与社区反馈（非 NVIDIA 自评）

### 6.1 最重要的负面独立报告：GitHub Issue #69（2026-06-06）

第三方用户 Naoya TAKENAKA（0xNOY）报告：**18 类多类检测任务中，LocateAnything 输出损坏的文本标签与错误检测框；同任务 Rex-Omni 全部正确检出**。URL：https://github.com/NVlabs/EAGLE/issues/69 。

1. MTP 训练策略未能把 AR 知识有效迁移到多类检测场景；
2. MoonViT+Qwen2.5 组合在该任务上不如单用 Qwen2.5。

并宣布：**已启动第二版迭代，目标 2 个月内发布**（截至 2026-06-07；本次调研截至 2026-08-29 未发现 v2 权重发布记录，记入 gaps）；临时缓解方案为「缓存图像特征 + 全类别批量推理」。该 issue 佐证了第 3.1 节的判断：**多类封闭集检测是其当前弱项，与论文主打的开放词汇/指代场景要分开看待**。

其他 issue：#75（微调时坐标归一化问题）、#84（`augmentation.py` 注释与实现不符，影响训练复现）。

## 7. 事实与观点区分清单
