**调研日期：2026-08-29。** 主题：多类检测 label corruption 的规避方案、官方承诺约 2026-08 中发布的 v2 是否落地、visual-prompt 权重是否放出。

**对预标注场景的直接含义**：多类预标注当下必须走 `batch_infer.py` 多类 query（`</c>` 连接）+ Hybrid Mode；18 类场景已被官方承认不可靠，官方临时方案也只自称 "improves label consistency" 而非根治。基于 v1 写 LoRA 存在返工风险——官方已确认根因在预训练（MTP 迁移不足、MoonViT+Qwen2.5 初始化组合），v2 大概率换底座，v1 的 LoRA adapter 届时可能不兼容；但推理管线层（batch scheduler、`</c>` query 格式、Hybrid 回退）设计上与权重解耦，返工面较小。

## 1. 缺陷本体与官方承认（GitHub Issue #69）

**Issue**：[(LocateAnything) Label corruption and incorrect detections observed in 18-class object detection](https://github.com/NVlabs/EAGLE/issues/69)，由用户 0xNOY 于 **2026-06-06** 提交，**至今 open**，无 assignee/label/milestone，无关联 PR。

- **复现场景**：18 类目标检测，与 Rex-Omni 对比测试。报告原文表述：Rex-Omni "Detected all objects accurately with correct labels"；LocateAnything "Output corrupted text labels and incorrect bounding boxes in the same 18-class scenario"。具体错乱文本只在 issue 附带的两张截图里（网页抓取无法读图，未取得具体错乱字符串——见 gaps）。
- 报告者自己当时在查根因，并问官方「是否有针对传入大量类别的推荐配置」。

**官方回复（issue 下唯一一条评论，即「官方承认」的出处）**：作者 **exiawsh**（author_association: COLLABORATOR；也是后续 visual prompt fine-tuning commit 的提交者），时间 **2026-06-07T08:05:41Z**（issue 提交次日）。要点：

1. **承认缺陷**：感谢报告者的 "detailed feedback and the comprehensive comparative testing"，确认团队自己也在多类目标检测中观察到类似退化（similar degradation in multi-class object detection）。
2. **根因 1**："Multi-Task Pretraining (MTP)" 未能把自回归（AR）知识有效迁移到多类检测场景（did not effectively transfer the autoregressive knowledge to the multi-class detection scenario）。
3. **根因 2**：MoonViT backbone 与 Qwen2.5 的组合在该任务上表现不如单独用 Qwen2.5。
4. **v2 承诺原文**：团队「已经启动 LocateAnything 的第二迭代」（"we have already launched the second iteration of LocateAnything"），「目标在未来 2 个月内发布」（"targeting a release within the next 2 months"），并承诺发布后通知报告者。
5. **临时规避方案原文**：建议「缓存图像特征并对全部类别同时做 batch inference」（"caching image features and performing batch inference across all classes simultaneously"），称其 "significantly reduces inference overhead and improves label consistency"，且该优化也会随 upcoming release 一并发布。

> 注：「已启动第二迭代训练」一事目前**仅有此条官方评论这一个来源**，无任何独立佐证（单一来源）。

**到期推算**：2026-06-07 + 2 个月 ≈ **2026-08-07**。今天是 2026-08-29，**已过期约 3 周**，且无延期公告（见下节证据）。

### 1.1 论文层面的补充：这不是纯解码 bug

中文技术社区（莫叶何竹《LocateAnything技术小结》转述论文）指出，论文本身分析了 "Format Irregularity" 失败模式：**多类别、多实例场景中模型在类别边界处犹豫，导致结构 token 混乱**（例如生成 `<box><211></ref><911><887></box>` 这类把结构 token（`</ref>`）与坐标 token 混排的畸形序列）。这与 #69 官方说的「MTP 未把 AR 知识迁移到多类场景」相互印证：**多类退化既有解码层成因，也有预训练能力层成因**——因此纯调解码模式（Hybrid/Slow）只能部分缓解，无法根治，这正是官方选择重训第二版的理由。此判断为本人基于两源的推导，标注为分析而非引文。

## 3. 多类 label corruption 的规避方案（当下可用的三层）

### 层 1：官方 #69 给的方案——多类合并 batch inference

官方临时建议「caching image features + batch inference across all classes」对应 **2026-06-12 发布的 batch inference 工具链**（Embodied README Updates: "[2026/06] Release batch inference with the optional `la_flash` runtime"）：

- `batch_infer.py`：JSONL/image-query batch inference CLI；`batch_utils/`：「batched hybrid MTP/NTP scheduler and sampling runtime」——这正是「一次调度全部类别」的实现载体（README 未直说「缓存图像特征」，该映射为本人在两处信息间的对应，标注为推导）。
- 多类 query 格式：类别用 `</c>` 连接成单条 query，例如官方示例：

```bash
python batch_infer.py --model . --attn la_flash --vision-attn flash_attention_2 \
  --scheduler pipeline --batch-size 4 --image /path/image.jpg --query "person</c>car"
```

- worker API 侧有 `detect_batch` 接口处理多 image/class 对。
- 性能数据（README 原样引用）：A100 4K probe 上 sdpa 8.26 s / 35.12 GB peak reserved，la_flash 8.0314 s / 11.71 GB；`la_flash` 用 FlashAttention varlen 实现稀疏 range plan，无需编译自定义 C++/CUDA 扩展，**仅限推理/评测，训练仍走标准代码路径**。
- 注意：官方对该方案的自评是 "improves label consistency"（改善）而非修复——18 类场景的可靠性仍无保证。

### 层 2：内置解码模式兜底（Hybrid / Slow）

Embodied README 与 HF 模型卡给出三种推理模式：

- **Fast Mode（MTP）**：全并行出框，最大吞吐，面向 on-device robotics；
- **Hybrid Mode（默认）**："MTP by default with NTP fallback on format irregularity or spatial ambiguity"——检测到格式异常/空间歧义即回退自回归逐 token 解码，"the compromised block is discarded and generation reverts to the last verified prefix"（丢弃受损块、回滚到最后验证前缀）；
- **Slow Mode**：纯自回归坐标解码，"maximum stability"，官方定位即 "high-precision labeling and offline evaluation"——**预标注场景如果走单类逐条 query，Slow Mode 是最稳的档位**（此推荐为本人基于官方定位的推导）。

### 层 3：社区实践（观点，非官方）

Reddit r/computervision 有帖子《Has anyone tried using LocateAnything to train YOLO based models?》讨论用其做 auto-labeling；社区建议是**同时跑多个自动标注模型、对输出不一致的样本做人工核验**。属社区观点，非官方方案。

### 方案缺口提醒

「类别分批 query（如每批 ≤N 类多次前向）」这种最直觉的绕法**没有任何官方或社区数据支持其有效性**——#69 根因指向预训练层面的多类能力缺失，分批只是缩小每次的多类规模，是否规避了触发条件（多少类开始退化）**无公开数据**（18 类触发是唯一实测点，单一来源）。这是当前公开信息的真实空白。

## 4. visual-prompt 权重状态：仍是 "future version"，已放出 LoRA 脚本

Embodied README（raw 原文，2026-06-24 版）：

- "The currently released `nvidia/LocateAnything-3B` weights do **not** support visual prompt inference out of the box."
- "Visual-prompt-capable weights will be released in a future version."（顶部 Note 与 Visual Prompt Fine-Tuning 小节各出现一次，后者写作 "Official visual-prompt-capable weights will be released in a future version."）

**已放出的替代路径**（2026-06-24 commit "Add visual prompt fine-tuning support"，对应 Updates "[2026/06] Release visual prompt fine-tuning script ... with LoRA fine-tuning for efficient adaptation"）：

- 脚本：`shell/locate-anything-lora-visual-prompt.sh`；
- 用法：在数据配置中 "Add `visual_prompt: true` to the datasets that should be converted into visual prompt training samples"，用自己的 visual prompt 数据做 LoRA 微调。

即**官方当前对 visual-prompt（图上画框/点指代）的答案是「自己 LoRA 微调」，官方权重无任何时间表**；HF 模型卡甚至连这条预告都没写（模型卡信息滞后于代码库 README）。相邻佐证：issue #81（2026-06-18，"Is it possible to fine tune the base model with lora, or any support planned?"）仍 open；#86 直接问 visual prompt 支持计划零回复。

## 5. 「现在基于 v1 写 LoRA 和管线是否返工」的判断依据（事实归纳）

- **返工风险高（权重层）**：v2 官方根因陈述涉及 MTP 预训练方案与 MoonViT+Qwen2.5 初始化组合两条——若 v2 调整 backbone 组合（去 MoonViT 或换初始化），**基于 v1 训的 LoRA adapter 大概率不兼容新底座**（需重训）；官方自己放出的 visual-prompt LoRA 脚本也预示「官方权重未出、社区先微调」的过渡形态。
- **返工风险低（管线层）**：batch scheduler（`batch_utils`）、`</c>` 多类 query 格式、`detect_batch` worker API、Hybrid/Slow 模式选择，这些接口是模型无关的推理外壳，v2 落地后大概率沿用。
- **时间预期**：官方 "within the next 2 months"（2026-06-07 起）已过期约 3 周且零沟通（GitHub 无 commit、issue 无跟进），**无法给出新的可靠时间估计**；若项目节奏按 v1 的「论文 → code 5 天 → batch inference 16 天 → LoRA 脚本 28 天」推，second iteration 训练+评测周期本就更长，逾期方向上不意外，但纯属推测（标注为分析）。
